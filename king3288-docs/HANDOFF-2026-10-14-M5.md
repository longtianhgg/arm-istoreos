## System and immutable constraints
- Board: KING3288 RK3288 ARMv7 4× Cortex-A17, 2 GiB DDR, 8 GiB production eMMC, Realtek RTL8211E PHY addr 0, UART2 115200.
- Production without SD: Ubuntu 20.04.3 Linux 4.4.189 on eMMC, previously boot-verified. No further eMMC write or original U-Boot/Trust changes. With experimental SD: original Rockchip U-Boot 2017.09 distro/extlinux, p1 FAT32 zImage+rk3288-king3288.dtb, p2 ext4 iStoreOS, boot-verified; SD PARTUUID=4b328826-02. Latest SD kernel is Linux 6.6.144. The no-SD production fallback after latest iStoreOS card deployment has not been explicitly retested.
- Trust/TEE two memory banks: 0x0+0x08400000; 0x09200000+0x76e00000. Keep timer@ff810000 disabled, UART2, GMAC RGMII TX 0x30 RX 0x10, PHY@0, ACT8846, SYR827/828, working MMC, TSADC CRU TSHUT and GPIO0_B2 pwr_hold pin conflict fix. No unrelated DTS refactor.
- Linux MMC naming changes between boots. User last verified SD as /dev/mmcblk0p2 (root ext4 UUID 52b116ba-1676-4cb6-a20e-9e80e340cf65), eMMC Ubuntu as /dev/mmcblk1p8 UUID 3d6b8cf4-922e-473b-bab1-bbdf3d8ad659. Rely on PARTUUID/UUID. fstab entry disabled automatic eMMC p8 mount; this was reboot-verified.
- Prior Linux 4.4 TX checksum offload corruption was real, but the current 6.6 iStoreOS boot DHCP, ARP/ICMP, DNS and HTTPS worked with RX/TX checksum ON. No need to disable offload without fresh evidence. Current PHY at 100M because user reported network cable constraint, do not retune RGMII or dwell on 100M negotiation now. MAC was seen varying across boots and its stable source remains an open issue.
